# 단계별 프롬프트

## 사용 전 확인

- 모든 단계는 `01_공통지침.md`의 시스템 프롬프트가 적용된 상태에서 보냅니다.
- 각 단계의 **입력**을 함께 제공합니다. 사내 AI가 저장소를 직접 읽을 수 있으면 경로만 주고, 대화형(파일 첨부)만 가능하면 파일을 첨부합니다.
- 사내 AI가 저장소에 직접 접근하지 못하고 첨부만 되는 경우:
  - 한 번에 **한 모듈 또는 화면 5~10개 분량**씩만 보냅니다.
  - 이전 단계 산출물(카탈로그 JSON)은 필요한 부분만 잘라 함께 보냅니다.
- `[ ]`로 표시된 부분은 매번 바꿔 넣습니다.
- **사람 검토** 표시가 있는 단계는 검토가 끝나기 전에 다음 단계로 넘어가지 않습니다(`04_검토_운영_가이드.md` 체크리스트 참고).

| P0 | 코드베이스 개요 조사 | 간단 확인 |

## P0. 코드베이스 개요 조사

**목적**: 이후 단계를 어떻게 나눠 분석할지 정하기 위해 구조와 기술 스택을 파악합니다.
**입력**: 소스 루트 디렉터리 트리(깊이 3~4), `settings.gradle(.kts)`, 앱 모듈 `build.gradle(.kts)`, `AndroidManifest.xml`

```text
[P0 코드베이스 개요 조사]

첨부한 디렉터리 구조와 빌드·매니페스트 파일을 분석해서 project_overview.md를 작성해줘.
아직 개별 화면이나 버튼은 분석하지 않는다. 구조 파악만 한다.

다음 항목을 조사해줘.
1. 모듈 목록: 모듈 이름, 경로, 역할(앱/기능/공통/라이브러리), 화면(UI)을 포함하는지 여부
2. UI 기술: XML View, ViewBinding/DataBinding, Jetpack Compose 중 무엇을 쓰는지,
   모듈별 비율 추정(근거 파일 예시 포함)
3. 화면 구성 방식: Activity 중심 / Single Activity + Fragment / Compose Navigation 여부
4. 내비게이션: navigation graph XML 위치, Compose NavHost 위치, 자체 라우터 클래스 여부
5. 딥링크: 매니페스트의 intent-filter scheme/host, 딥링크 처리 클래스 위치
6. 문구 리소스: strings.xml 위치, 지원 언어(values-xx 폴더 목록)
7. 서버 주도 UI / 동적 UI 흔적: Remote Config, Feature Flag, 서버 응답으로 레이아웃을 그리는 코드 위치
8. WebView 사용 위치
9. 지도 렌더링: 지도 뷰 클래스, 네이티브(JNI/so) 여부
10. 주행·결제 관련 모듈/패키지 후보 (안전 분류에 쓸 목록, 이름과 근거)
11. 빌드 변형(buildType/flavor): 스테이지 빌드 설정, 난독화(minifyEnabled, shrinkResources) 설정

마지막에 "분석 단위 계획"을 표로 제시해줘.
- 이후 P1~P2를 몇 개의 묶음으로 나눌지, 묶음별 모듈/패키지, 예상 화면 수, 우선순위
- 우선순위는 사용 빈도가 높고 안전 위험이 낮은 기능을 먼저(예: 검색, 즐겨찾기, 설정)

출력 형식: 03_산출물_스키마의 "project_overview.md" 목차를 따른다.
```

## P1. 화면 카탈로그

**목적**: 테스트 대상이 되는 모든 화면의 목록과 진입 방법을 만듭니다.
**입력**: P0 결과, `AndroidManifest.xml`, navigation XML, 해당 묶음의 Activity/Fragment/Composable 화면 파일 목록과 내용

```text
[P1 화면 카탈로그 — 묶음: [묶음 이름 / 모듈 목록]]

project_overview.md의 분석 단위 계획에 따라, 이번 묶음의 화면 목록을 screen_catalog 형식으로 만들어줘.
기존 screen_catalog.json이 첨부되어 있으면 기존 screen_id는 그대로 유지하고 새 화면만 추가해.

화면으로 보는 단위:
- Activity, Fragment, DialogFragment, BottomSheetDialogFragment
- Compose의 NavHost composable(route) 목적지, 전체 화면 Dialog/BottomSheet
- 화면 안의 탭(ViewPager/TabLayout)은 탭마다 별도 화면으로 등록하고 parent_screen_id로 연결

화면마다 다음을 채워줘(근거 파일:라인 필수).
1. screen_id, 화면 이름(한국어, 사용자 관점), 구현 클래스, 레이아웃 파일 또는 Composable 함수
2. 화면 타이틀 문구(strings 키와 실제 문구)
3. 진입 방법
   - 딥링크가 있으면 전체 URI 형식과 필요한 파라미터
   - Intent로 직접 실행 가능하면 Activity 이름과 extras
   - 둘 다 없으면 "UI 경로만 가능"으로 표시 (P3에서 경로를 채움)
4. 전제조건: 로그인 필요 여부, 위치 권한, 특정 데이터 필요 여부(예: 즐겨찾기 1개 이상), 플래그
5. 안전 등급(1차): SAFE / CAUTION / BLOCKED
   - 화면 자체가 주행 안내·결제 진행 화면이면 BLOCKED (이 화면은 테스트 대상에서 제외)
6. 테스트 범위 메모: 서버 주도 UI 비중, WebView 여부, 지도 포함 여부

주의:
- 개발용/디버그 전용 화면은 dev_only: true로 표시만 하고 제외하지는 않는다.
- 같은 레이아웃을 여러 화면이 공유하면 각각 등록하고 shared_layout 필드에 표시한다.
```

## P2. 요소 카탈로그

**목적**: 화면마다 테스트에 쓸 버튼·메뉴·입력창의 식별자와 속성을 모읍니다. **가장 중요한 단계**입니다.
**입력**: 대상 화면(5~10개)의 screen_catalog 항목, 해당 레이아웃 XML(include 포함), menu XML, 화면 클래스/ViewModel 코드, 관련 strings.xml 항목

```text
[P2 요소 카탈로그 — 화면: [screen_id 목록]]

첨부한 화면들에 대해 elements/<screen_id>.json을 화면마다 하나씩 만들어줘.

대상 요소:
- 클릭/롱클릭 가능한 모든 요소(버튼, 메뉴 항목, 탭, 토글, 체크박스, 라디오, 리스트 항목, 아이콘)
- 입력 요소(EditText, TextField, 검색창)
- 테스트 판정에 쓸 표시 요소(타이틀, 오류 문구, 빈 화면 안내, 토스트·스낵바 문구, 결과 개수)
- include/merge된 레이아웃과 공용 컴포넌트 안의 요소도 펼쳐서 포함한다(origin_layout에 원래 파일 표시)

요소마다 다음을 채워줘. 소스에서 확인되지 않으면 UNKNOWN.
1. locator 원천 값
   - resource_id: 레이아웃의 android:id 이름(예: btn_favorite). 런타임 전체 ID는
     "{{PACKAGE}}:id/btn_favorite" 형식으로 추정해 runtime_id_guess에 적는다.
     (라이브러리 모듈은 패키지가 다를 수 있으니 확실하지 않으면 inferred)
   - compose_test_tag: Modifier.testTag 값
   - content_desc: contentDescription 값(문자열 리소스면 키와 실제 문구 둘 다)
   - text: 표시 문구(strings 키 + {{LANG}} 기준 실제 문구). 코드에서 동적으로 설정하면 그 로직 요약
   - view_type: Button, TextView, ImageView, RecyclerView item, Compose Button 등
2. 위치 맥락: 부모 컨테이너 ID, 리스트 항목이면 리스트 ID와 항목 레이아웃 파일
3. 노출 조건: 기본 visibility, 코드에서 visibility를 바꾸는 조건(로그인, 플래그, 데이터 유무)
4. 동작
   - action_type: navigate / toggle / input / submit / dialog / external / none
   - 핸들러 위치(파일:라인), 핸들러가 하는 일 요약
   - 이동하는 화면이면 target_screen_id (모르면 UNKNOWN)
   - 서버 API를 호출하면 API 이름(엔드포인트 주소는 쓰지 않음)
5. 안전 등급: SAFE / CAUTION / BLOCKED + 근거
   - 핸들러를 끝까지 따라가 판단한다. 주행/결제/외부 실행으로 이어지면 BLOCKED.
   - 데이터를 바꾸지만 되돌릴 수 있는 동작(즐겨찾기 추가/삭제, 설정 변경)은 CAUTION.
6. 추천 locator: 아래 우선순위로 첫 번째 사용 가능한 것과, 대체 locator 1개
   1) resource_id (화면 안에서 유일할 때)
   2) compose_test_tag
   3) content_desc
   4) 부모 resource_id + 자식 조건 (예: 리스트 항목 안의 버튼)
   5) text (문구 변경·다국어에 약함 → stability: low)
   6) 좌표 (사용 금지, 다른 방법이 없으면 stability: none으로 표시만)
   - 화면 안에서 같은 resource_id가 여러 번 나오면(리스트, include 중복) unique: false로 표시
7. 식별자 품질: OK / NO_ID / DUPLICATE_ID / DYNAMIC / COMPOSE_NO_TAG / ICON_NO_DESC

주의:
- 하나의 요소에 resource_id, text, content_desc가 모두 있으면 모두 기록한다.
- 라벨이 형제/자식 TextView에만 있는 "익명 클릭 컨테이너"는 label_source에 실제 라벨을
  가진 요소를 적는다(런타임에서 이 패턴의 주행 버튼이 필터를 우회한 사고가 있었다).
- 리스트 항목은 항목 하나를 대표로 기록하고 is_list_item: true로 표시한다.
```

## P3. 화면 전이·진입 방법

**목적**: 어떤 화면에서 무엇을 누르면 어디로 가는지, 그리고 테스트 시작 화면에 가장 안정적으로 들어가는 방법을 정리합니다.
**입력**: screen_catalog.json, elements/*.json(action_type이 navigate인 항목), navigation XML, 딥링크 처리 코드

```text
[P3 화면 전이·진입 방법]

screen_catalog와 요소 카탈로그를 바탕으로 transitions.json을 만들어줘.

1. 전이(edge) 목록
   - from_screen_id, element_key, to_screen_id, 조건(로그인 등), 근거
   - 요소 카탈로그의 target_screen_id가 UNKNOWN인 항목은 navigation XML, startActivity,
     navController.navigate, 자체 라우터 호출을 따라가 채운다. 끝까지 못 찾으면 UNKNOWN 유지.
   - 뒤로가기/닫기로 돌아가는 전이는 기록하지 않는다(자동 처리).
2. 화면별 진입 전략(entry) — 테스트가 이 화면에서 시작할 때 쓸 방법, 우선순위 순
   1) deeplink: 전체 URI
   2) intent: adb shell am start 명령 형태(액티비티, extras)
   3) ui_path: 앱 시작 화면(홈)에서 이 화면까지 가는 가장 짧은 탭 경로(element_key 목록)
   - ui_path에 BLOCKED 요소가 포함되면 그 경로는 쓰지 않는다. 다른 경로가 없으면
     "진입 불가(안전)"로 표시한다.
   - 서버 주도 UI 요소(홈 카드, 배너)를 거치는 경로는 unstable: true로 표시한다.
3. 도달 불가 화면 목록: 어떤 전이로도 들어갈 수 없는 화면(딥링크·푸시 전용, 사용 안 하는 화면 후보)

출력: transitions.json (03 스키마) + 요약 표(화면별 진입 방법 종류)
```

## P4. 안전 분류 점검 (필수 사람 승인)

**목적**: 실물 단말에서 실제 주행·결제가 시작되는 사고를 막기 위해, 안전 분류만 따로 다시 검사합니다.
**입력**: 전체 요소 카탈로그 중 safety가 SAFE/CAUTION인 항목, P0의 주행·결제 모듈 목록, 해당 핸들러 코드

```text
[P4 안전 분류 점검]

이 단계의 유일한 목적은 "BLOCKED여야 하는데 SAFE/CAUTION으로 분류된 요소"를 찾는 것이다.
새 요소를 추가하거나 다른 필드를 고치지 않는다.

1. P0에서 찾은 주행·결제·외부 실행 관련 클래스/패키지 목록을 기준으로,
   그 클래스를 시작하거나 호출하는 모든 코드 위치를 찾는다
   (startActivity, startService, navigate, 결제 SDK 호출, Intent.ACTION_CALL/ACTION_VIEW 등).
2. 그 호출 위치에 도달하는 클릭 핸들러를 거꾸로 추적해서, 해당 요소의 현재 safety 값을 확인한다.
3. 반대로 safety가 SAFE/CAUTION인 요소 중 다음에 해당하는 것을 모두 다시 확인한다.
   - 문구에 공통지침의 주행/결제 키워드가 들어 있는 요소
   - 핸들러가 다른 모듈의 함수를 호출해서 끝까지 확인하지 못한 요소(inferred)
   - 라벨이 없는 아이콘·익명 컨테이너
   - 홈 화면 바로가기, 하단 탭, 플로팅 버튼
4. 결과를 safety_review.md로 작성한다.
   - 표 1: BLOCKED로 올려야 할 요소 (element_key, 현재 값, 근거 경로 전체: 요소 → 핸들러 → 호출 → 위험 동작)
   - 표 2: 판단 보류(사람 확인 필요) 요소와 사유
   - 표 3: 과차단 의심(BLOCKED지만 실제로 안전해 보이는) 요소 — 변경 제안만 하고 값은 바꾸지 않는다
   - 새로 발견한 위험 문구가 있으면 "블랙리스트 추가 제안" 목록으로 따로 적는다

BLOCKED를 낮추는 변경은 절대 직접 하지 않는다. 낮추는 것은 사람이 승인한 뒤에만 한다.
```

## P5. 식별자 품질 리포트 (개발팀 전달용)

**목적**: 자동화가 어려운 요소를 모아서 개발팀에 식별자 보강을 요청합니다.
**입력**: 전체 요소 카탈로그, transitions.json

```text
[P5 식별자 품질 리포트]

요소 카탈로그의 id_quality와 locator stability를 집계해서, 개발팀에 보낼 identifier_report.md를 작성해줘.
독자는 앱 개발자다. 테스트 자동화 용어보다 "어느 파일 어느 뷰에 무엇을 추가해 달라"는 형태로 쓴다.

1. 요약: 전체 요소 수, 품질별 개수와 비율, 모듈별 비율 표
2. 우선 보강 목록 (최대 50개, 우선순위 순)
   - 우선순위 기준: TC에 자주 쓰일 핵심 기능(검색, 즐겨찾기, 설정, 경로 결과 화면) >
     stability가 low/none > 리스트 항목 안의 버튼
   - 항목마다: 화면, 요소 설명, 파일:라인, 현재 상태, 요청 내용(추가할 id/testTag/contentDescription 이름 제안)
   - BLOCKED 요소는 보강 대상에서 제외한다(자동 조작하지 않으므로)
3. 일괄 요청 사항
   - Compose 화면: testTagsAsResourceId = true 적용 위치 제안
   - 아이콘 버튼 contentDescription(접근성 개선과 같은 작업임을 명시)
   - 중복 ID 정리가 필요한 공용 컴포넌트
4. 화면 진입 보강: 딥링크가 없어 ui_path로만 들어갈 수 있는 주요 화면 목록과 딥링크 추가 요청
5. 테스트 훅 요청(스테이지 빌드 한정): 팝업·광고 끄기, Remote Config 고정, 위치 주입,
   테스트 계정 로그인 상태 주입, 리소스 이름 난독화 예외 — 각각 필요한 이유를 카탈로그 근거로 설명
```

## P6. 런타임 대조 (정적 카탈로그 ↔ 실제 앱)

**목적**: 소스에서 뽑은 식별자가 실제 앱에서도 그대로 보이는지 확인해 "검증된 카탈로그"를 만듭니다.
**입력**: 요소 카탈로그, 크롤러 결과 `sitemap.json`과 화면별 UI XML 덤프(가능하면), P0의 난독화 설정

이 단계는 AI가 직접 대조하기보다 **대조 스크립트를 만들게** 하는 것이 정확합니다.

```text
[P6 런타임 대조 — 대조 스크립트 작성]

정적 요소 카탈로그(elements/*.json)와 런타임 크롤링 결과(sitemap.json, 화면별 UI XML 덤프)를
대조하는 Python 스크립트 verify_catalog.py를 작성해줘.

입력:
- elements/*.json (03 스키마의 element 형식)
- sitemap.json: 첨부한 샘플 구조를 따른다(screens[].fingerprint, activity, elements 등)
- xml_dumps/<fingerprint>.xml: uiautomator 덤프

처리:
1. 런타임 화면 ↔ screen_id 매칭: activity 이름, 화면 타이틀 문구, 요소 resource-id 겹침 비율로 점수를 매겨
   가장 높은 화면에 매칭. 점수가 기준(기본 0.6) 미만이면 unmatched로 둔다.
2. 요소 대조: 매칭된 화면마다 카탈로그 요소의 runtime_id_guess, content_desc, text가
   XML에 있는지 확인
3. 결과 상태:
   - VERIFIED: 실제로 발견, 식별자 일치
   - ID_MISMATCH: 같은 위치/문구의 요소는 있으나 resource-id가 다름(난독화·패키지 차이 의심) → 실제 ID 기록
   - NOT_SEEN: 화면은 방문했지만 요소가 보이지 않음(노출 조건 의심)
   - SCREEN_NOT_VISITED: 크롤러가 화면에 도달하지 못함
   - RUNTIME_ONLY: 런타임에는 있는데 카탈로그에 없음(서버 주도 UI, 동적 생성 의심)
4. 출력: verified_catalog.json(요소마다 verification 필드 추가)과 verify_report.md(상태별 집계, 화면별 표)

요구사항:
- Python 3.9+, 표준 라이브러리만 사용
- 입력 경로는 명령행 인자로 받는다
- 매칭 기준값, 가중치는 상단 상수로 분리
- 단위 테스트(pytest) 포함: 매칭/상태 판정 함수 각각
```

스크립트를 실행한 뒤, 결과 리포트를 다시 AI에게 주고 아래를 요청합니다.

```text
[P6-2 대조 결과 해석]
첨부한 verify_report.md를 보고,
1) ID_MISMATCH 패턴(규칙적인 이름 변환인지, 특정 모듈만인지)을 분석해 카탈로그 일괄 수정 규칙을 제안하고
2) NOT_SEEN 요소마다 카탈로그의 노출 조건으로 설명되는지 확인하고, 설명되지 않는 것을 목록화하고
3) RUNTIME_ONLY 요소를 서버 주도 UI / 카탈로그 누락 / 광고로 분류해줘.
카탈로그를 직접 고치지 말고 수정 제안 목록으로 출력해.
```

## P7. 정책 → 테스트케이스

**목적**: 정책 문서를 읽고, 검증된 카탈로그에 있는 화면·요소만 사용해 TC를 만듭니다.
**입력**: 정책 문서(한 기능 영역씩), 해당 영역의 screen_catalog·verified_catalog·transitions 발췌, 기존 TC(있으면)

```text
[P7 정책 → TC — 기능 영역: [영역 이름]]

첨부한 정책 문서를 분석해서 이 기능 영역의 테스트케이스를 testcases/<영역>.json으로 만들어줘.

1단계: 정책 분해 (먼저 출력)
- 정책 문서의 검증 가능한 규칙을 하나씩 뽑아 policy_rules 표로 정리한다.
  rule_id, 원문 인용(문장 그대로), 규칙 요약, 유형(기능/입력검증/권한/표시/한도/예외)
- 모호하거나 서로 충돌하는 규칙은 "확인 필요"에 올린다. 해석해서 채우지 않는다.

2단계: TC 작성
- 규칙마다 정상 흐름 1개 이상 + 해당되면 경계값·오류·권한 없음 케이스를 만든다.
- 모든 단계는 카탈로그의 element_key로 표현한다. 카탈로그에 없는 요소가 필요하면
  그 단계를 "MISSING_ELEMENT: 설명"으로 쓰고 TC 상태를 blocked_by_catalog로 둔다. 요소를 지어내지 않는다.
- 시작 화면은 transitions의 진입 전략(entry)을 참조한다.
- 기대결과는 확인 가능한 형태로 쓴다.
  - 요소 존재/부재, 텍스트 일치(strings 키 기준), 화면 이동(screen_id), 값 변경
  - 데이터가 매번 바뀌는 항목(ETA, 거리, 교통정보, 검색 결과)은 값이 아니라 조건으로 쓴다
    (예: "ETA 텍스트가 'N분' 형식", "결과 1개 이상")
  - 지도 위에서만 확인 가능한 결과는 check_type: vision으로 표시한다
- 자동화 가능 여부(automation)
  - auto: 카탈로그 요소만으로 실행·판정 가능
  - semi: 일부 단계가 비전 판정이나 사람 확인 필요
  - manual_only: BLOCKED 요소 조작, 실제 주행·결제, 본인인증이 필요한 경우
- 안전: BLOCKED 요소를 조작하는 단계를 넣지 않는다. 정책 검증에 꼭 필요하면 manual_only TC로 만든다.
- CAUTION 요소(데이터 변경)를 쓰는 TC는 teardown에 원래 상태로 되돌리는 단계를 넣는다.

3단계: 추적표
- rule_id ↔ tc_id 매핑 표. TC가 없는 규칙과 그 이유를 표시한다.
```

## P8. TC → 자동 테스트 스크립트

**목적**: 승인된 TC를 결정적으로 실행되는 스크립트로 바꿉니다. 실행할 때 AI가 필요 없어야 합니다.
**입력**: 승인된 testcases/<영역>.json, verified_catalog 발췌, transitions(entry), 기존 공통 코드(있으면)

```text
[P8 TC → 스크립트 — 영역: [영역 이름]]

승인된 TC를 {{TEST_FRAMEWORK}} 스크립트로 변환해줘. 구조는 아래를 따른다.

디렉터리 구조
  pages/        화면별 Page Object (카탈로그에서 생성)
  flows/        진입 전략(딥링크/intent/ui_path) 공통 함수
  tests/<영역>/ TC별 테스트 함수
  core/         드라이버 생성, 대기, 안전 가드, 스크린샷/로그 수집

1. Page Object (pages/<screen_id 소문자>.py)
   - 카탈로그의 추천 locator를 상수로 정의하고, 대체 locator를 함께 둔다
   - 요소 상수 옆 주석에 element_key와 근거 파일:라인을 단다
   - BLOCKED 요소는 locator를 정의하되 클릭·입력 메서드를 만들지 않는다(존재 확인 메서드만)
2. 안전 가드 (core/safety.py) — 반드시 포함
   - 모든 클릭/입력은 safe_tap(), safe_input()만 통한다. 드라이버의 click()을 직접 부르지 않는다
   - safe_tap은 클릭 직전에 대상 요소의 text/content-desc/resource-id와 하위 텍스트를
     공통지침의 블랙리스트 키워드로 검사하고, 걸리면 예외를 던지고 클릭하지 않는다
   - 클릭 후 현재 activity가 주행/결제 화면 목록에 해당하면 즉시 테스트를 중단하고 앱을 종료한다
3. 테스트 (tests/<영역>/test_<tc_id 소문자>.py)
   - 함수 이름과 docstring에 tc_id, 정책 rule_id
   - setup: flows의 진입 함수 사용(딥링크 우선)
   - 단계마다 명시적 조건 대기(요소 표시, 화면 전환). 고정 sleep 금지
   - 판정은 TC의 check_type대로. vision 판정은 core/vision_check.py의 함수 호출로 분리하고
     기본은 skip 표시(나중에 연결)
   - teardown: TC의 원복 단계 실행, 실패해도 다음 테스트에 영향 없게
   - 실패 시 스크린샷, UI XML 덤프, logcat 일부를 저장
4. 금지
   - 좌표 탭, xpath 인덱스(예: //android.widget.Button[3])
   - 비밀번호·토큰 하드코딩(환경변수 사용)
   - BLOCKED 요소 조작
5. 함께 출력
   - 실행 방법(README 단락), 필요한 환경변수 목록
   - 변환하지 못한 TC와 사유(예: blocked_by_catalog, vision 필요)
```

## P9. 실행 결과 분석·실패 분류

**목적**: 스케줄 실행에서 실패한 테스트의 원인을 분류하고 다음 행동을 제안합니다.
**입력**: 실패 테스트 목록, 테스트별 로그·스크린샷·UI XML 덤프·logcat 발췌, 해당 TC와 Page Object, 앱 버전

```text
[P9 실행 결과 분석 — 실행: [날짜/빌드 번호]]

첨부한 실패 결과를 테스트별로 분석해서 run_analysis.md를 작성해줘.

테스트마다:
1. 실패 지점: 단계 번호, 실패 유형(요소 못 찾음/판정 불일치/타임아웃/앱 크래시/안전 가드 차단)
2. 원인 분류 (하나 선택, 근거 필수)
   - APP_BUG: 앱이 정책·TC 기대결과와 다르게 동작 (스크린샷/XML로 실제 동작 설명)
   - SCRIPT_BROKEN: 앱 UI 변경으로 locator·흐름이 바뀜 (XML에서 찾은 새 식별자 제시)
   - ENV: 네트워크, 서버, 기기, 팝업·광고, 위치, 로그인 만료
   - FLAKY: 타이밍. 재실행 시 통과 이력 있음
   - SAFETY_STOP: 안전 가드가 차단함 (이건 항상 사람에게 보고)
   - UNKNOWN
3. 다음 행동
   - APP_BUG: 이슈 초안(제목, 재현 단계, 기대/실제 결과, 첨부 목록, 관련 정책 rule_id)
   - SCRIPT_BROKEN: Page Object/카탈로그 수정 diff 제안 (직접 반영하지 않음)
   - ENV/FLAKY: 재실행 여부, 환경 조치 제안
   - SAFETY_STOP: 무엇이 차단됐는지, 카탈로그 안전 분류 수정 필요 여부

마지막에 요약 표: 원인별 개수, 이번 실행의 통과율, 반복 실패(3회 이상) 테스트 목록.
앱 버그로 단정하기 어려우면 APP_BUG로 분류하지 말고 UNKNOWN으로 두고 확인 방법을 적는다.
```

## P10. 소스 변경 영향도 분석 (릴리스마다)

**목적**: 새 릴리스의 소스 변경으로 깨질 카탈로그 항목과 스크립트를 미리 찾습니다.
**입력**: 이전 릴리스와 새 릴리스 사이의 diff(레이아웃·strings·menu·navigation·화면 클래스 위주), 현재 카탈로그, 스크립트가 사용하는 element_key 목록

```text
[P10 변경 영향도 — [이전 버전] → [새 버전]]

첨부한 소스 diff를 분석해서 impact_report.md를 작성해줘.

1. 변경 분류
   - 식별자 변경: android:id/testTag/contentDescription 이름 변경·삭제·추가
   - 문구 변경: strings.xml 값 변경(키 동일, 값 변경 포함)
   - 화면 구조 변경: 레이아웃 계층 변경, 화면 추가·삭제, 전이·딥링크 변경
   - 동작 변경: 클릭 핸들러 변경, 노출 조건 변경
   - 안전 관련 변경: 주행·결제·외부 실행 호출이 새로 추가되거나 다른 버튼으로 옮겨진 경우 (최우선 보고)
2. 영향 매핑
   - 변경마다 영향을 받는 element_key, screen_id, 그 요소를 쓰는 TC·테스트 파일
   - 영향 등급: BREAK(확실히 실패) / RISK(실패 가능) / INFO(영향 없음)
3. 조치 제안
   - 카탈로그 갱신 항목(새 값, 근거 파일:라인)
   - Page Object 수정 diff 제안
   - 새로 필요한 TC(새 화면·기능)와 폐기할 TC
4. 안전 재검사 대상: 안전 관련 변경이 있으면 P4를 해당 범위로 다시 실행하라고 명시

카탈로그와 스크립트를 직접 고치지 말고 제안으로만 출력한다.
```

## 공통: 품질이 떨어질 때 보내는 보정 프롬프트

```text
[검증 요청]
방금 출력에서 근거(evidence)가 없거나, 첨부한 파일에서 확인되지 않는 값을 모두 찾아서
표로 보여줘. 각 항목을 "근거 확인됨(파일:라인)" 또는 "UNKNOWN으로 변경"으로 정리하고,
수정된 JSON을 다시 출력해. 새로운 항목은 추가하지 마.
```

```text
[스키마 검사 요청]
방금 출력한 JSON을 03_산출물_스키마와 비교해서 누락 필드, 추가 필드, 타입 불일치,
허용되지 않은 enum 값을 모두 나열하고 고친 버전을 출력해.
```

```text
[이어서 진행]
이전 응답의 "다음 작업"부터 이어서 진행해. 이미 출력한 항목은 다시 출력하지 말고,
기존 screen_id/element_key는 그대로 사용해.
```
