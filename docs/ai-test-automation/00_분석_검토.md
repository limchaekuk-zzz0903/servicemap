# 소스코드 기반 테스트 자동화 — 분석·검토

## 1. 결론

**소스코드에서 식별자를 미리 뽑아두는 방식은 타당하고, 앞서 구상한 방식보다 훨씬 안정적입니다.**
AI가 화면을 보고 버튼을 "추측"하던 단계를 미리 만든 **요소 카탈로그를 "조회"하는 단계**로 바꿀 수 있습니다.

단, 한 가지 조건이 붙습니다.

> 소스코드는 "화면에 **나올 수 있는** 것"만 알려줍니다. "**지금 실제로 나오는** 것"은 앱을 실행해야만 알 수 있습니다.
> 그래서 **정적 카탈로그(소스) + 런타임 검증(크롤러/실행)**을 합쳐 "검증된 카탈로그"를 만들어야 합니다.

정적 분석만으로 모든 정보를 확정하고 스크립트를 만들면, 실행하는 순간 숨겨진 요소, 서버에서 내려오는 UI, 팝업 때문에 상당수가 실패합니다.
이미 가진 크롤러(`crawler.py`, `sitemap.json`)가 런타임 검증 역할을 맡으면 됩니다.

## 2. 소스코드에서 얻을 수 있는 정보

| 소스 위치 (Android 기준) | 얻는 정보 | 테스트 자동화에서의 용도 |
|---|---|---|
| `res/layout/*.xml` | `android:id`, 뷰 타입, `contentDescription`, 기본 `visibility` | locator(resource-id)의 원천 |
| `res/menu/*.xml` | 메뉴 항목 ID, 제목 | 옵션 메뉴, 하단 탭 locator |
| `res/values*/strings.xml` | 문구 키 → 실제 표시 문구(언어별) | text locator, **정책 문구 ↔ UI 문구 연결** |
| Jetpack Compose 코드 | `Modifier.testTag`, `semantics { contentDescription }` | Compose 화면 locator (testTag 없으면 식별 불가) |
| `AndroidManifest.xml` | Activity 목록, `intent-filter`, **딥링크 스킴** | 화면 목록, **전제조건 화면으로 바로 이동** |
| `res/navigation/*.xml`, Compose NavHost route | 화면 간 이동 경로, 인자 | 화면 전이 그래프 |
| 클릭 핸들러 (`setOnClickListener`, `onClick =`) | 버튼을 누르면 실행되는 코드, 이동하는 화면 | 기대결과, **안전 분류(주행/결제 판정)** |
| `visibility`/`isVisible`/`if (...)` 조건 | 요소가 보이는 조건(로그인, 플래그, 데이터 유무) | 전제조건 정의 |
| Remote Config / Feature Flag 키 | 서버 설정에 따라 바뀌는 UI | 테스트 환경 고정 대상 |
| WebView 로딩 URL | 웹 화면 진입점 | WebView 컨텍스트 전환 대상 |

### 기존 방식에는 없던 큰 이점 4가지

1. **딥링크로 전제조건을 바로 만듭니다.**
   "설정 > 지도 > 글자 크기 화면에서…" 같은 TC를 실행할 때, 화면을 하나씩 탭해서 이동하지 않고 딥링크 한 번으로 진입합니다.
   지금 크롤러가 "TMAP 홈은 광고·동적 콘텐츠 때문에 경로 재생이 자주 실패"하는 문제(HANDOFF.md 8번)를 근본적으로 피할 수 있습니다.

2. **안전 분류가 정확해집니다.**
   지금은 버튼 **문구(키워드)**로만 주행·결제를 판정합니다. 그래서 '안전운행' 버튼이 필터를 통과해 실제 내비게이션에 들어간 사고가 있었습니다(config.py 주석, 2026-07-12).
   소스에서는 **버튼이 실제로 무엇을 실행하는지**(예: `TmapNaviActivity` 시작, 결제 SDK 호출)를 보고 판정할 수 있습니다. 문구와 상관없이 막을 수 있습니다.

3. **변경 영향도를 출시 전에 알 수 있습니다.**
   소스 diff에서 바뀐 ID나 화면을 찾아 "이번 릴리스에서 깨질 스크립트 목록"을 미리 뽑을 수 있습니다. 실패한 다음 고치는 것이 아니라 실패하기 전에 고칩니다.

4. **정책 문서와 화면이 문구로 연결됩니다.**
   정책 문서의 "즐겨찾기는 최대 N개" 같은 문장과 `strings.xml`의 오류 문구를 연결해 TC의 기대결과를 정확하게 쓸 수 있습니다.

## 3. 소스코드만으로는 알 수 없는 것

| 항목 | 이유 | 대응 |
|---|---|---|
| 실제로 보이는지 여부 | 로그인 상태, 데이터 유무, 플래그 값에 따라 달라짐 | 런타임 검증(크롤러) 결과와 대조 |
| 서버 주도 UI (홈 카드, 배너, 이벤트) | 레이아웃이 서버 응답으로 결정됨 | 스테이지 서버 설정 고정 또는 테스트 대상에서 분리 |
| 리스트 항목 개수, 내용 | 검색 결과, POI 데이터는 런타임 데이터 | 조건 기반 판정("1개 이상", "형식 일치") |
| 지도(엔진) 위 요소 | 네이티브 렌더링(OpenGL)이라 뷰가 없음 | 지도 API·디버그 훅 요청, 비전 판정 |
| A/B 실험군 | 사용자별로 다른 UI | 테스트 계정의 실험군 고정 |
| 같은 ID의 여러 화면 재사용 | `include`, 공용 컴포넌트 | **화면 ID + 요소 ID** 조합으로 식별 |
| 난독화 | 빌드 설정에 따라 리소스 이름이 바뀔 수 있음 | 스테이지 빌드에서 실제 resource-id와 대조 확인 |
| 타이밍 | 애니메이션, 로딩 | 스크립트에서 명시적 대기(조건 대기) |

## 4. 바뀌는 전체 구조

```
[앱 소스코드] ──(AI 정적분석)──▶ 정적 카탈로그 ─┐
                                 화면/요소/전이/딥링크   │
                                                        ├─▶ 검증된 카탈로그 ──┐
[스테이지 앱] ──(crawler.py)──▶ sitemap.json ───────┘   (실제 resource-id,    │
                                 (런타임 화면/요소)        노출 여부 확인)       │
                                                                              ▼
[정책 문서] ──────────────────────────────────▶ (AI) TC 생성 ──▶ 사람 검토
                                                                              │
                                              (AI) 스크립트 생성 ◀──────────────┘
                                              Page Object = 카탈로그에서 자동 생성
                                                                              │
                                              CI 스케줄 실행 (AI 없이 결정적 실행)
                                                                              │
                     (AI) 실패 분석·분류 ◀────────────────────────────────────┘
                     앱 버그 → 이슈 / 스크립트 깨짐 → 수정안 / 환경 → 재실행

[소스 diff(릴리스)] ──(AI)──▶ 영향도 분석 ──▶ 카탈로그·스크립트 선제 수정
```

**이전 구상과의 차이**

| 단계 | 이전 (화면 기반) | 변경 (소스 기반) |
|---|---|---|
| 요소 정보 | 실행 중 XML·스크린샷으로 추측 | 소스에서 미리 확정, 실행은 확인만 |
| 화면 이동 | 탭을 반복해 이동 | 딥링크·Intent로 직접 진입 |
| 안전 판정 | 버튼 문구 키워드 | 문구 + **핸들러가 실제로 하는 일** |
| 녹화 분석 | 영상·trace 분석으로 스크립트 생성 | 필요 없음. 카탈로그 + TC로 직접 생성 |
| 유지보수 | 실패 후 수정 | 소스 diff로 사전 수정 |

AI 실행·녹화 단계는 **카탈로그를 검증하고, 소스로 알 수 없는 부분(지도, 서버 UI)을 보완하는 용도**로 축소됩니다.

## 5. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| AI가 소스에 없는 ID를 만들어냄(환각) | 스크립트가 처음부터 실패 | 모든 항목에 **근거(파일:라인) 필수**, 근거 없으면 `UNKNOWN`. 사람이 10% 샘플을 검증 |
| 코드베이스가 커서 한 번에 분석 불가 | 누락, 품질 저하 | **모듈·화면 단위로 나눠** 분석하고 결과를 병합 |
| 공용 컴포넌트의 ID 중복 | 엉뚱한 요소 탭 | 화면 범위 locator (부모 컨테이너 + ID) |
| 서버·플래그 의존 UI | 실행할 때마다 결과 다름 | 스테이지 환경 고정, 플래그 값 명시 TC |
| 안전 분류 누락 | 실물 단말에서 실제 주행·결제 실행 | 안전 분류를 **별도 단계(P4)로 이중 점검**, 블랙리스트는 런타임에도 유지 |
| 카탈로그가 앱 버전과 어긋남 | 오래된 정보로 스크립트 생성 | 카탈로그에 **앱 버전·커밋 해시** 기록, 릴리스마다 재생성 |
| 소스·정책 문서 보안 | 유출 | 사내 허가 AI만 사용, 산출물에 비밀값·개인정보 금지 규칙 |

## 6. 판단

| 항목 | 평가 |
|---|---|
| 기술 실현 가능성 | **높음** (Android 기준. iOS는 `accessibilityIdentifier`로 같은 방식 적용 가능) |
| 기존 방식 대비 안정성 | 크게 향상 (locator 근거 확보, 딥링크 진입, 사전 영향도 분석) |
| 가장 큰 남은 과제 | 지도 영역, 서버 주도 UI, 동적 데이터 판정 |
| 성패를 가르는 요소 | ① 개발팀 협조(테스트 훅) ② 단계별 사람 검토 ③ 카탈로그 버전 관리 |

### 개발팀에 요청할 테스트 훅 (스테이지 빌드 한정)

효과가 큰 순서입니다.

1. **식별자 보강**: 식별자 없는 주요 버튼에 `resource-id`/`contentDescription`, Compose는 `testTag` + `testTagsAsResourceId = true`.
2. **딥링크 보장**: 테스트 대상 주요 화면을 딥링크로 열 수 있게.
3. **팝업·광고 끄기 플래그**: 이벤트 팝업, 광고, 업데이트 안내를 끄는 디버그 옵션.
4. **설정 고정**: Remote Config, A/B 실험군을 테스트 계정 기준으로 고정.
5. **위치 주입**: mock location 허용 또는 디버그용 위치 설정 Intent.
6. **로그인 상태 주입**: 테스트 계정 토큰 주입(비밀번호 입력 자동화 대신).
7. **난독화 예외**: 스테이지 빌드에서 리소스 이름 유지.
