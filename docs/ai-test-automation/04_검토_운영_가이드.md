# 검토·운영 가이드 (사람용)

AI가 만든 결과물은 **사람이 검토한 뒤에만** 다음 단계로 넘깁니다. 이 문서는 단계별 검토 체크리스트, 진행 계획, 운영(스케줄 실행) 방법을 정리합니다.

---

## 1. 진행 계획 (권장)

처음부터 앱 전체를 하지 않습니다. **한 기능 영역으로 전체 사이클을 먼저 완주**한 뒤 넓힙니다.

| 단계 | 범위 | 할 일 | 완료 기준 |
|---|---|---|---|
| 1. 파일럿 | 1개 영역 (예: 즐겨찾기 또는 설정) | P0 → P1~P4 → P6 → P7 → P8, CI 1회 실행 | TC 10~20개 중 auto 70% 이상 스크립트화, 연속 5회 안정 통과 |
| 2. 확장 | 핵심 영역 3~5개 (검색, 즐겨찾기, 설정, 내정보, 경로 결과 화면) | 영역마다 반복, P5 리포트를 개발팀에 전달 | 스모크 세트 매일 실행 |
| 3. 운영 | 전체 | P9 일상화, P10 릴리스마다 실행 | 릴리스 전 영향도 리포트 정착 |

파일럿 영역은 **안전 위험이 낮고(주행·결제와 거리가 멀고) 딥링크가 있는 영역**을 고릅니다.

## 2. 단계별 검토 체크리스트

### P0 코드베이스 개요
- [ ] 모듈 목록이 실제 저장소와 맞는다 (빠진 기능 모듈 없음)
- [ ] 주행·결제·외부실행 관련 클래스 목록에 알려진 주행 화면(예: `TmapNaviActivity`)이 포함되어 있다
- [ ] 분석 단위 계획의 묶음 크기가 AI가 한 번에 처리할 수 있는 수준이다 (화면 5~10개)

### P1 화면 카탈로그
- [ ] 무작위 화면 5개를 골라 클래스·레이아웃 경로가 실제로 존재한다
- [ ] 딥링크가 적힌 화면 3개를 실제로 `adb shell am start -d "<uri>"`로 열어본다
- [ ] 주행 안내 화면, 결제 화면이 `BLOCKED`로 표시되어 있다

### P2 요소 카탈로그 — 샘플 10% 검증
- [ ] 무작위 요소 10%에 대해 `evidence`의 파일:라인을 열어 ID·문구가 일치한다
- [ ] 환각 비율(근거와 불일치) **5% 이하**. 넘으면 해당 묶음을 다시 생성한다
- [ ] `UNKNOWN` 비율이 비정상적으로 높지 않다 (높으면 입력 파일이 부족했던 것)
- [ ] 리스트 항목 안의 버튼이 `parent_child` locator로 정의되어 있다

### P3 화면 전이·진입 방법
- [ ] 주요 화면 3개의 `ui_path`를 실제 앱에서 손으로 따라가 본다
- [ ] `ui_path`에 BLOCKED 요소가 없다

### P4 안전 분류 — **필수 승인**
- [ ] "BLOCKED 상향 필요" 항목을 모두 반영했다
- [ ] "판단 보류" 항목을 개발자 또는 기획자에게 확인했다
- [ ] 과차단 해제는 **두 사람 이상 확인한 뒤에만** 반영했다
- [ ] 새 위험 문구를 크롤러 `config.py` 블랙리스트와 `core/safety.py`에 반영했다
- [ ] 승인란에 검토자·날짜를 기록했다

### P5 식별자 품질 리포트
- [ ] 요청 내용이 개발자가 바로 작업할 수 있을 만큼 구체적이다 (파일:라인, 이름 제안)
- [ ] 내부 비밀값이 들어 있지 않다

### P6 런타임 대조
- [ ] `VERIFIED` 비율 확인 (파일럿 목표 70% 이상)
- [ ] `ID_MISMATCH`가 많으면 난독화·패키지 문제인지 먼저 확인
- [ ] `RUNTIME_ONLY` 중 광고가 아닌 것은 카탈로그 누락으로 보고 P2 재실행

### P7 정책 → TC — **필수 검토**
- [ ] 정책 규칙 인용이 원문과 정확히 일치한다
- [ ] 모든 단계가 카탈로그에 있는 `element_key`를 쓴다 (없는 키 = 환각)
- [ ] 동적 데이터의 기대결과가 값이 아니라 조건으로 쓰여 있다
- [ ] BLOCKED 요소 조작 단계가 없다
- [ ] CAUTION 요소를 쓰는 TC에 원복(teardown)이 있다
- [ ] 추적표에서 TC 없는 규칙의 사유가 타당하다
- [ ] 검토 후 `status`를 `approved`로 바꾼다

### P8 스크립트 — **코드 리뷰 필수**
- [ ] 모든 클릭·입력이 `safe_tap`/`safe_input`을 통한다 (`grep -n "\.click()" tests pages`로 확인)
- [ ] 좌표 탭, xpath 인덱스, 고정 `sleep`이 없다
- [ ] 비밀번호·토큰 하드코딩이 없다
- [ ] 로컬에서 각 테스트를 3회 연속 실행해 결과가 같다
- [ ] **첫 실행은 에뮬레이터에서** 하고, 실물 단말은 그다음에 한다

## 3. 사내 AI 사용 요령

| 상황 | 방법 |
|---|---|
| AI가 저장소를 직접 읽을 수 있음 | 경로만 주고 "해당 경로의 파일을 직접 열어 확인"하도록 지시. 근거 라인 정확도가 가장 높음 |
| 대화에 파일 첨부만 가능 | 한 번에 화면 5~10개 분량. 레이아웃 XML + 화면 클래스 + 관련 strings만 추려서 첨부 |
| 응답이 중간에 끊김 | "이어서 진행" 보정 프롬프트 사용. 출력 단위를 화면 1~3개로 줄임 |
| 근거 없는 값이 섞임 | "검증 요청" 보정 프롬프트 사용 |
| JSON 형식이 틀림 | "스키마 검사 요청" 보정 프롬프트 사용, 또는 `python -m json.tool`로 먼저 검사 |
| 대화가 길어져 앞 규칙을 잊음 | 새 대화를 열고 공통지침 + 필요한 산출물 발췌만 다시 제공 |

**산출물은 대화에만 두지 말고** 반드시 Git 저장소(`qa-automation/catalog/`)에 커밋합니다. 다음 단계의 입력이 되고, 버전(앱 버전·커밋)별로 비교할 수 있어야 합니다.

## 4. 운영 (스케줄 실행)

### 실행 세트

| 세트 | 대상 | 주기 | 기기 |
|---|---|---|---|
| 스모크 | `priority: P1` | 스테이지 빌드 배포마다 + 매일 아침 | 에뮬레이터 1대 |
| 회귀 | `P1` + `P2` | 매일 야간 | 에뮬레이터 + 실물 1대 |
| 전체 | 전체 auto | 주 1회 + 릴리스 후보 | 실물 여러 기종 |

### 파이프라인

```
스케줄/빌드 이벤트
  → 기기 준비 (앱 설치, 테스트 계정 로그인 상태 확인, 위치 설정, 팝업 끄기 플래그)
  → pytest 실행 (실패 시 1회 자동 재실행 → 재실행 통과는 FLAKY로 기록)
  → 결과 수집 (JUnit XML, 스크린샷, XML 덤프, logcat)
  → P9: 사내 AI로 실패 분류
  → 사람 확인 → 이슈 등록 / 스크립트 수정 PR
```

- 기존 `run_stage.sh`(Appium 서버 상태 확인·재기동, 반복 실행) 구조를 CI 작업의 시작점으로 쓸 수 있습니다.
- **정기 실행에는 AI를 쓰지 않습니다.** AI는 실패 분석(P9)과 변경 대응(P10)에만 씁니다. 그래야 결과가 재현되고 비용이 일정합니다.
- 실물 단말에서 안전 가드(`SAFETY_STOP`)가 한 번이라도 발생하면 **해당 세트를 즉시 중지**하고 원인 확인 전까지 재개하지 않습니다.

### 릴리스마다

1. 새 버전 소스 diff로 **P10** 실행
2. 안전 관련 변경이 있으면 해당 범위로 **P4** 재실행
3. BREAK 항목 카탈로그·Page Object 수정 후 회귀 세트 실행
4. 카탈로그 `meta.app_version`, `commit` 갱신 후 커밋

### 관리 지표

| 지표 | 의미 | 목표 (파일럿 기준) |
|---|---|---|
| 카탈로그 VERIFIED 비율 | 정적 분석 정확도 | 70% → 90% |
| TC 채택률 | AI TC 중 수정 없이/경미 수정으로 승인된 비율 | 60% 이상 |
| 자동화율 | approved TC 중 스크립트화된 비율 | 70% 이상 |
| Flaky 비율 | 재실행으로 통과한 비율 | 5% 이하 |
| 실패 원인 정확도 | P9 분류가 사람 판단과 일치한 비율 | 80% 이상 |
| 사전 탐지율 | 릴리스 후 깨진 스크립트 중 P10이 미리 지목한 비율 | 80% 이상 |
| 안전 사고 | 실물 단말에서 주행·결제 진입 | **항상 0** |

## 5. 역할 분담

| 역할 | 하는 일 |
|---|---|
| QA 자동화 담당 | 단계 프롬프트 실행, 산출물 검토·커밋, 스크립트 리뷰, CI 운영 |
| 기능 QA / 기획 | 정책 문서 제공, TC 검토(P7), 정책 해석 질문 응답 |
| 앱 개발자 | P5 식별자 보강, 테스트 훅 구현, P4 판단 보류 항목 확인 |
| 보안 담당 | 사내 AI에 소스·정책을 넣는 범위 승인, 산출물 비밀값 점검 기준 |
